### 0.2 Hard constraints honoured throughout
No torch import in the orchestrator. `studio.domain` stays standard-library only (`hashlib`, `json`, `fractions`, `dataclasses`, `enum` are stdlib) and never imports pydantic, the registry or engines. GPU work stays out of process. Approval gates hold no GPU lease. Imported assets are first-class. Outputs never overwrite approved versions. ComfyUI is externally managed. LTX is used only through its unchanged CLI. Everything stays generic. NVML free VRAM is the primary measurement, with no double counting. All thresholds (including K, T and the per-binding limits below) are provisional until calibrated.

## A. Slot and SlotBinding (UD-1)

### A.1 Problem (verified)
- `Shot.selected_take_id` (`production.py:252`) is one mutable pointer, and it can point only at a take. An imported asset cannot be "the shot's result", and the selection keeps no history.
- Approval subjects are `take | asset_version | gate` (`workflow.py:171-174`). No subject kind exists for "this version occupies this production position".
- Accepted text already names the concepts: ADR-0004:11-12 lists "slot bindings" among the DB contents, and ADR-0006:31-33 defines "Slot (role in the production), SlotBinding (append-only history)". The domain does not model them (`assets.py:10`, ADR-0010 U-6).

### A.2 Alternatives
| | A-1 Shot output binding only | **A-2 Owner-scoped Slot + append-only SlotBinding (recommended)** | A-3 Slots implicit in `CreativeSpec.references` |
|---|---|---|---|
| Shape | Replace `selected_take_id` with a per-shot binding history to an AssetVersion | `Slot` entity owned by project/scene/shot (deliverable later), INPUT and OUTPUT direction, constraints; `SlotBinding` rows with supersession | A reference role *is* the slot; binding history keyed by (shot, role) |
| Imported assets fill slots | Output only | Yes, inputs and outputs | Yes, inputs only |
| Required/optional and constraints declared independently of a spec | No | Yes | No (lives inside each spec) |
| Approval subject | Per-shot binding | Per binding (`SLOT_BINDING`) | Awkward: the subject would be a reference inside a spec |
| Cross-shot continuity | Not expressible | `SlotLink` + `upstream_slot_binding_id` | Not expressible |
| Cost | Small | Medium (new module, validation, approvals) | Small, but blocks deliverables and continuity later |
| Fit with ADR-0006:31-33 | Partial | Full | Partial (no Slot entity) |

**Recommendation (PROPOSED): A-2.** A-1 does not let imports or continuity frames feed a shot's inputs. A-3 makes a slot's requirements depend on whichever spec happens to reference it, and it cannot carry an approval cleanly.

### A.3 Entities (PROPOSED; new module `src/studio/domain/slots.py`)
Naming: the registry already uses "binding" (`CreativeSpec.binding_id` is a *registry capability* binding). To avoid confusion, slot-binding fields and ids always use the full name `slot_binding_id` / `SlotBindingId`.

```
SlotOwnerKind(StrEnum): PROJECT | SCENE | SHOT            # DELIVERABLE added with the timeline milestone (I-11)
SlotDirection(StrEnum): INPUT   # consumed when the owner is generated (e.g. a shot's start_frame)
                        OUTPUT  # the owner's result (e.g. a shot's main clip)
                        MEMBER  # an element of a project/scene collection (e.g. a recurring product packshot)
Cardinality(StrEnum):   ONE | ORDERED_MANY
SlotState(StrEnum):     ACTIVE | RETIRED                  # plan apply retires, never deletes (ADR-0004)

Slot(frozen):
  slot_id: SlotId; project_id: ProjectId
  owner_kind: SlotOwnerKind; owner_id: str               # must reference an existing owner of that kind
  role: str (ROLE_RE); direction: SlotDirection           # (owner_kind, owner_id, direction, role) unique
  media_type: MediaType                                   # from studio.domain.vocab
  required: bool
  cardinality: Cardinality = ONE; max_items: int | None   # max_items only for ORDERED_MANY
  constraints: SlotConstraints                            # min/max width/height, aspect (Rational), min/max duration_ms,
                                                          # fps (Rational | None), needs_audio (bool | None); all optional
  requires_selection_approval: bool = True
  state: SlotState = ACTIVE

SlotBindingState(StrEnum): ACTIVE | SUPERSEDED | WITHDRAWN   # SUPERSEDED/WITHDRAWN are terminal
SlotBinder(StrEnum): HUMAN | WORKFLOW

SlotBinding(frozen):
  slot_binding_id: SlotBindingId; slot_id: SlotId
  sequence: int                       # 1..n per slot, contiguous: the append-only history order
  position: int | None                # ORDERED_MANY: 1-based item position; ONE: None
  version_id: VersionId; sha256: str  # subject: an AssetVersion (generated, derived or IMPORTED) pinned to content
  take_id: TakeId | None              # provenance when the version is an output of a take
  upstream_slot_binding_id: SlotBindingId | None   # continuity: this version was derived from that binding's version
  supersedes_slot_binding_id: SlotBindingId | None
  state: SlotBindingState = ACTIVE
  bound_by: SlotBinder; bound_by_name: str; bound_at: datetime (aware); reason: str

SlotLinkRelation(StrEnum): LAST_FRAME_OF | FIRST_FRAME_OF | SAME_CONTENT
SlotLink(frozen): upstream_slot_id, downstream_slot_id, relation    # declarative continuity, data only
```
- **Append-only history.** A binding is never edited. Rebinding a ONE slot creates binding *n+1* with `supersedes_slot_binding_id = n`, and binding *n* goes to SUPERSEDED. Unbinding without a replacement moves the live binding to WITHDRAWN. Reordering an ORDERED_MANY slot supersedes the affected bindings with new positions. This satisfies ADR-0004:15-16 ("never deletes ... history") and ADR-0006:32.
- **Binding subject is always an AssetVersion.** This is what lets imported assets fill slots (UD-1). Rejected alternative: a Take as the subject, since an import has no take. `take_id` is optional provenance. When set, `version_id` must be among `take.output_version_ids`.
- **Approval.** A new `ApprovalSubjectKind.SLOT_BINDING` and a new `ApprovalPurpose.SELECTION` ("may this version occupy this slot?"). A selection is a creative decision, so `authority` must be HUMAN in M0.3a (I-5).
- **Relation to take reviews.** For an OUTPUT slot, a selection approval of a binding whose `take_id` is set requires that the take has a current APPROVED CONTENT_REVIEW. A UI may record both in one action, but they remain two records.

### A.4 Owners, cardinality and resolution
| Owner kind | Typical use (generic, not perfume-specific) | Now? |
|---|---|---|
| PROJECT | recurring brand element, product packshot, voice-over master (MEMBER) | yes |
| SCENE | location plate, scene music bed (MEMBER or INPUT) | yes |
| SHOT | `start_frame`/`mask`/`reference_*` (INPUT); the main clip (OUTPUT) | yes |
| DELIVERABLE / timeline | ordered clips, music, titles (MEMBER, ORDERED_MANY) | deferred to the timeline milestone (I-11) |

Cardinality options: ONE only (simplest; deliverables impossible); **ONE + ORDERED_MANY (recommended)**; plus UNORDERED_MANY (no current need). For ORDERED_MANY, the positions of ACTIVE bindings must be exactly 1..n, and n ≤ `max_items` when set.

**Resolution rule (PROPOSED).** `AssetRef` is unchanged. When a shot task is resolved (a later milestone), each INPUT slot of the shot with an ACTIVE, currently approved binding yields a resolved `AssetRef(role=slot.role, asset_id=version.asset_id, version_id, sha256)`. An authored reference in `CreativeSpec.references` must not reuse the role of one of the same shot's INPUT slots (`slot.role_conflict`). Every shot needs at least one OUTPUT slot (`slot.shot_no_output`).

### A.5 Fate of `Shot.selected_take_id`
Options: (i) keep it as a cached pointer synchronized with the OUTPUT slot, which leaves two sources of truth; (ii) keep it deprecated and ignored; **(iii) remove it (recommended)**. "The selected take" becomes the `take_id` of the ACTIVE binding of the shot's required OUTPUT slot. Nothing is persisted yet, so no migration is needed. `validation.py:172-183` is rewritten as follows. A shot is **APPROVED** iff every required OUTPUT slot has an ACTIVE binding with a current HUMAN SELECTION approval, and every take named by those bindings is APPROVED. A shot is **IN_REVIEW** iff some take is PRODUCED/APPROVED and the condition above does not hold.

### A.6 Cross-shot continuity (example, generic)
Shot S1 has an OUTPUT slot `main` (video). Shot S2 has an INPUT slot `start_frame` (image) and `SlotLink(S1.main → S2.start_frame, LAST_FRAME_OF)`.
1. S1.main is bound to version V1 (from take T1).
2. A derivation job (frame extraction) produces image V2 with a lineage edge V1→V2 (`TRANSFORM`).
3. S2.start_frame is bound to V2 with `upstream_slot_binding_id` = the S1.main binding.

If S1.main is later rebound, the S2.start_frame binding's selection approval goes stale (`upstream_binding_changed`). Rebinding S2.start_frame then changes S2's resolved inputs, so S2's creative identity changes and its take reviews go stale (section D). Note: the vocabulary has no frame-extraction `Operation`. Adding one changes `vocab.py` and the registry tables, so it is deferred (I-11). Until then, a continuity binding may use any imported or derived image version.

### A.7 Binding states, staleness and validation
- Staleness is never a binding state. It belongs to the *selection approval* (append-only approvals). Triggers are listed in D.2, rows 16-20.
- **Structural** checks in `validate_snapshot` (always): `slot.owner_missing`, `slot.role_duplicate`, `slot.duplicate_binding` (two ACTIVE on a ONE slot), `slot.position_gap`, `slot.sequence_gap`, `slot.supersession` (supersedes must be the same slot's previous sequence), `slot.media_mismatch` (version's asset media type ≠ slot media type), `slot.hash_mismatch` (binding `sha256` ≠ version object hash), `slot.take_provenance` (take must list the version and be PRODUCED/APPROVED), `slot.continuity_lineage` (an upstream binding requires a lineage path from the upstream version), `slot.link_cycle`, `slot.link_media` (LAST/FIRST_FRAME_OF: video→image; SAME_CONTENT: same media), `slot.role_conflict`, `slot.shot_no_output`.
- **Readiness** checks in a separate pure function `check_slot_readiness(snapshot, owner) -> issues`, used before task resolution or gate passage and not part of integrity: `slot.missing_required`, `slot.unapproved` (no current SELECTION approval while `requires_selection_approval`), `slot.version_unavailable` (version not AVAILABLE: CORRUPT, RETIRED, QUARANTINED), `slot.constraint_mismatch` (probe metadata violates constraints; unknown metadata is reported as `slot.constraint_unknown`, never assumed to pass).

## B. Hashing and fingerprints (UD-2, UD-3)

### B.1 Problem (verified)
- `HASH_ALGORITHM = "sha256"` exists (`assets.py:40`), but no fingerprint function exists. `TaskSpec.fingerprint_input` (`workflow.py:71-74`) is the resolved creative form only: no algorithm tag, and no model, engine or template identity. `domain-model.md:46` ("no hash function is chosen") and ADR-0010 U-4 are stale under UD-2.
- **DM-4** (`canonical.py:32-33`): the integer range -2^63..2^64-1 fits neither int64 nor uint64.
- **DM-5** (`production.py:78-82`, `canonical.py:9`): `fps=24` and `fps=24.0` serialize differently, which is a false creative change.
- **DM-6** (`production.py:118`, `:159`): reference order changes the hash, duplicate roles are accepted, and elements are not type-checked.
- **MIN-2**: canonical JSON is Python-specific (`json.dumps` float repr), not RFC 8785.

### B.2 Alternatives
| | B-1 One creative `spec_hash` (status quo, fixed) | B-2 One full fingerprint for everything | **B-3 Two levels: creative identity hash + task fingerprint (recommended)** |
|---|---|---|---|
| Drives approval staleness | yes | yes: an execution/model change would stale approvals, violating **UD-3** | identity hash only |
| Detects model/template/engine change for reproduction/caching | no | yes | task fingerprint |
| UD-6 eligibility test ("execution-only change?") | needs a separate diff | impossible from the hash | `identity_hash` equal ⇔ execution-only change |
| Complexity | low | low | medium |

A variant, B-4 (a Merkle tree of component digests), is folded into B-3: the task fingerprint payload stores component digests, so "what changed" is cheap to report.

**Recommendation (PROPOSED): B-3**, with three digest families:
1. **Object digest**: SHA-256 of raw bytes, 64 lowercase hex, stored bare in `ObjectRef.sha256` (ADR-0006 layout `objects/sha256/ab/cd/`). It is not enveloped: the bytes are the identity.
2. **Creative identity hash** `identity_hash`: envelope kind `creative_identity`. It drives staleness (UD-3) and UD-6 eligibility.
3. **Task fingerprint** `task_fingerprint`: envelope kind `task_fingerprint`. It drives reproduction, caching and resume compatibility.

### B.3 Envelope (PROPOSED; new module `src/studio/domain/fingerprint.py`)
```
envelope = {"alg": "sha256", "canonical_version": 2, "kind": <kind>, "payload": <payload>}
digest   = hashlib.sha256(canonical_bytes_v2(envelope)).hexdigest()        # 64 lowercase hex
Fingerprint(frozen): kind: FingerprintKind; alg: "sha256"; canonical_version: int; digest: str; complete: bool
  .key -> "<kind>/v<canonical_version>/sha256:<digest>"                    # text form for logs and DB
FingerprintKind(StrEnum): CREATIVE_IDENTITY | TASK_FINGERPRINT | EXECUTION_SPEC | RECOVERY_POLICY | STAGE_KEY
```
- Fingerprints of different `kind` or `canonical_version` are **never equal** (`Fingerprint.__eq__` compares all fields). Comparing across canonical versions answers "incomparable", never "same". Staleness decisions compare structured views (D.2), not digests across versions. The digest is a fast path within one version.
- `complete=False` when any component is unknown (for example, model file `sha256` is `null` in every shipped model YAML today). Incomplete fingerprints are stored but never used for caching or deduplication, and two incomplete fingerprints never count as a cache hit.
- The domain computes digests with stdlib `hashlib`. This is pure and allowed by the stdlib-only rule. It reverses the stale statement at `domain-model.md:46` and closes ADR-0010 U-4 (draft in F.3).

**`creative_identity` payload** (field names are fixed by this design):
`operation`; `capability` (= `binding_id`); `prompt`; `negative_prompt`; `width`; `height`; `fps` as `{"num","den"}` (reduced); `duration_ms` (int); `seed` (decimal **string**); `references` (sorted by `(role, index)`, each `{"role","index","sha256"}`); `parameters` (creative free parameters).
- **UD-6 adaptable fields.** A registry binding may declare, in `execution_only`, reserved fields from the allowlist `{width, height, duration_s}` (resolution and frame count, the UD-6 examples). For that binding, those fields leave the identity payload and go to the execution component. `fps` is never adaptable. Whether this reading of UD-6 is intended is question I-1(b).
- Excluded: database ids, execution parameters, model/template/engine identity, recovery policy.

**`task_fingerprint` payload:** `identity` (the identity digest); `execution` (the canonical execution parameters, including any adapted reserved fields); `models` (sorted by `(model_id, role)`, each `{"model_id","role","sha256","size_bytes"}`; directory models use the digest of a canonical manifest `[{path,size,sha256}]`); `template` (object digest of the resolved template file, or null until M2.1); `engine` (`{"engine_id","version"}`, for example the LTX git commit recorded per ADR-0003:19, the ComfyUI version, the ffmpeg version string). Input object hashes and the seed are covered transitively through `identity`. Managed environment values (TEMP/TMP/HF_HOME paths, REG-3) are excluded because they are not result-affecting.

**Other kinds:** `execution_spec` (diagnostics), `recovery_policy` (the C.2 snapshot digest; UD-7 "policy version"), and `stage_key` = `{task_fingerprint, stage}` (C.4 resume compatibility).

### B.4 Canonical form v2 (PROPOSED; `canonical.py`, `CANONICAL_VERSION = 2`)
| Rule | v1 (current) | **v2 (proposed)** |
|---|---|---|
| Serialization | Python `json.dumps(sort_keys, separators, ensure_ascii=False)` | **RFC 8785 (JCS)** output, implemented in stdlib |
| int vs float | type-preserving (`24` ≠ `24.0`, causing DM-5) | JCS number model: one numeric value, one text (`24` = `24.0` → `24`) |
| Integer range | -2^63..2^64-1 (DM-4) | JSON numbers limited to ±(2^53-1); larger values (seed, sizes) are typed fields encoded as decimal strings |
| Float text | Python `repr` (exponent at ≥1e16 / <1e-4) | ECMAScript `Number.toString` (exponent at ≥1e21 / <1e-6): shortest round-trip digits from `repr`, reformatted |
| -0.0, NaN, ±inf | -0.0→0.0; NaN/inf rejected | -0 → `0`; NaN/inf rejected |
| Keys | any `str`, sorted by code point | ASCII only (`PARAM_KEY_RE` and fixed field names). Code-point order = JCS UTF-16 order |
| Strings | unnormalized; lone surrogates rejected | unchanged (text is content; NFC and NFD differ on purpose). Escaping is identical to JCS for `ensure_ascii=False` |
| Sequences | order significant | order significant, **but** first-class collections are canonicalized before serialization (references sorted by `(role, index)`) |
| Typed first-class fields | `fps`, `duration_s` as int-or-float | `fps` = `Rational(num, den)` reduced (authored `24` → 24/1, `"24000/1001"` accepted, float rejected); `duration_s` authored as int/float/decimal string, normalized to `duration_ms: int`, rejected unless exact to 1 ms |

Alternatives considered: (i) keep v1 and fix DM-5 per field only. This is cheap, but digests stay Python-specific and no independent tool can produce golden vectors. **(ii) JCS over a restricted value domain (recommended).** Its output is byte-identical to RFC 8785 for every value v2 admits, so `sha256sum` over a hand-written canonical file can cross-check Python. (iii) Deterministic CBOR: no stdlib encoder, so it is rejected for the domain.

**DM-6 rules (PROPOSED, `CreativeSpec.__post_init__`):** every element must be an `AssetRef` (else `spec.reference_type`). `AssetRef` gains `index: int = 1` (≥1). `(role, index)` must be unique (`spec.reference_duplicate`), and a multi-valued role uses indices 1..n contiguously. The canonical form sorts by `(role, index)`, so authoring order never changes the hash.

### B.5 Field renames
`spec_hash` becomes `identity_hash` plus `task_fingerprint` on `Take`, `Job` and `Provenance`. In `RecoveryRule`, the `spec_hash` relation becomes an `identity` relation. Reproduction requires the same `identity_hash` and seed. A differing `task_fingerprint` makes it an *inexact* reproduction, recorded on the take (`exact: bool`), not an error.

### B.6 Golden test vectors (to author later in WT-A; none computed now)
Stored as `tests/domain/golden/fingerprint_v2.json` with `input`, `canonical_bytes` (hand-written and reviewed) and `digest`. Digests are computed in the first A3 session by **both** Python and `sha256sum` over the canonical bytes, so the two implementations check each other.
1. Minimal resolved T2I spec. 2. `fps: 24` vs `fps: 24.0` → same identity. 3. `fps: "24000/1001"`. 4. The same references in two orders → same identity. 5. A duplicate `(role, index)` → rejected. 6. Seed `2^64-1` → string `"18446744073709551615"`. 7. Free parameter `2^53` → rejected. 8. `-0.0` → `0`. 9. Prompt `"é"` NFC vs NFD → different. 10. Floats `1e21`, `1e-7`, `0.1`, `100.0` → JCS text. 11. Execution parameter change → same identity, different task fingerprint. 12. An unknown model digest → `complete=false`. 13. The same payload with `kind` changed → different digest. 14. RFC 8785 Appendix B number samples (serialization only).

## C. Recovery model (UD-4, UD-7, DM-10)

### C.1 Problem (verified)
`DEFAULT_MAX_INFRASTRUCTURE_RETRIES = 2` (`recovery.py:33-34`). RESUME counts against the same budget (`recovery.py:100-104`). `Job.max_infrastructure_retries` defaults to 2 (`workflow.py:33,94`). Validation sums retry and resume together (`validation.py:407-408`). The constant is exported (`__init__.py:44,89`) and documented (`domain-model.md:78-79`, `architecture.md:67` "max 2", ADR-0010 P-5). All of this contradicts UD-4 and UD-7. **DM-10:** `WAITING_RESOURCES → FAILED` (`states.py:229`) leaves no attempt and no error class, so no route leads to resource adaptation.

### C.2 Policy object and where it lives
```
# registry side (pydantic, WT-B), optional on EngineSpec (engine default) and BindingSpec (override)
recovery:
  max_infrastructure_retries: int | null   # null/absent = no automatic infrastructure retry
  max_resumes: int | null                  # null/absent = no automatic resume
  max_resume_depth: int | null             # consecutive RESUME chain cap; null = no resume-of-resume
# domain side (WT-A, stdlib dataclass)
RecoveryPolicySnapshot(frozen): source: "binding:<id>" | "engine:<id>" | "none"
                                max_infrastructure_retries: int | None; max_resumes: int | None
                                max_resume_depth: int | None; digest: Fingerprint (kind RECOVERY_POLICY)
Job.recovery_policy: RecoveryPolicySnapshot      # REQUIRED; no default value (UD-7)
```
| | **C-1 Registry (engine default + binding override) (recommended)** | C-2 Separate `config/recovery/*.toml` | C-3 `studio.toml` per binding |
|---|---|---|---|
| "per binding/engine policy" (UD-7) | native | keyed by id | keyed by id |
| Reviewed with the binding it governs | yes | separately | separately |
| Environment overlays can silently change it | no | no | **yes** (dev/test overlays): rejected |
| Extra loader/schema | none (extends existing schema; optional field, no `SCHEMA_VERSION` bump) | new loader | settings growth |

Override semantics: a binding `recovery` block **replaces** the engine block as a whole. Fields are not merged, which removes any ambiguity. With neither block present, the snapshot is `source: "none"` and all limits are `None`, which means no automatic recovery. **No shipped YAML gets a `recovery` block in M0.3a.** The values stay unset until the user sets them (I-8).

**Snapshot at creation:** the Job stores the full snapshot (limits and digest). A later registry change never alters a running job's budget, and validation needs no registry.

### C.3 Attempt causes and derived counters
```
AttemptEndCause(StrEnum): ENGINE | STUDIO_PROCESS | HOST_RESTART | USER_STOP
AttemptInitiator(StrEnum): AUTOMATIC | HUMAN
Attempt += cause: AttemptEndCause | None      # required iff state in {FAILED, INTERRUPTED}; FAILED ⇒ ENGINE
          initiated_by: AttemptInitiator; initiated_by_name: str | None (required for HUMAN)
          artifact_version_ids: tuple[VersionId,...]   # intermediate, resumable stage artifacts; allowed in any terminal state
          resume_artifact_sha256: str | None           # RESUME only; pins the reused artifact's bytes
          interrupted_boot_id: str | None              # set by startup marking
AttemptOrigin += MANUAL_RESTART                        # human-initiated re-run; never budgeted
```
Pure functions (`recovery.py`). Counters are **always derived from persisted attempt rows, never kept in memory** (UD-7):
- `consumes_budget(a)` = `a.state ∈ {FAILED, INTERRUPTED} ∧ a.cause is ENGINE` (engine-side failures consume, UD-7).
- `counts_toward_breaker(a)` = `a.state is INTERRUPTED ∧ a.cause ∈ {STUDIO_PROCESS, HOST_RESTART, USER_STOP} ∧ a.started_at is not None`. An attempt that never started does not inflate the breaker. USER_STOP is counted because UD-7 says so literally; see I-9.
- `retries_used(job)` = the number of AUTOMATIC attempts with origin INFRASTRUCTURE_RETRY whose predecessor `consumes_budget`. `resumes_used(job)` is the same for origin RESUME.
- After a non-budget interruption, an automatic follow-up (retry or resume) consumes nothing. It still counts as *automatic recovery*, so it is allowed only if the policy permits that kind (`None` ⇒ no automatic follow-up; a human may `MANUAL_RESTART`).
- Validation: `retries_used ≤ (max_infrastructure_retries or 0)`, `resumes_used ≤ (max_resumes or 0)`, resume chain depth ≤ `(max_resume_depth or 1)` for any RESUME. Codes: `recovery.retry_budget`, `recovery.resume_budget`, `recovery.resume_depth`, `recovery.not_permitted_by_policy`.

### C.4 Resume-of-resume and the stage artifact check
A RESUME attempt is valid only if all of the following hold:
1. `resume_artifact_version_id` is listed in `artifact_version_ids` of an earlier attempt of the **same job**.
2. Its `object_ref.sha256` equals `resume_artifact_sha256`.
3. Its provenance `stage_key` equals `stage_key(job.task_fingerprint, stage)`, and the job's task fingerprint is complete.
4. The version is AVAILABLE.
5. The chain of consecutive RESUME predecessors is no longer than `max_resume_depth`.

Codes: `recovery.resume_artifact`, `recovery.resume_hash`, `recovery.resume_stage_key`, `recovery.resume_depth`. Provenance gains `stage: str | None` and `stage_key: str | None`.

### C.5 DM-10: admission refusal and the route to resource adaptation
Alternatives: (i) a synthetic attempt row for the refusal (`PENDING → FAILED`, class RESOURCE). This is wrong, because an attempt means an execution try and it would distort attempt numbering and the breaker. **(ii) A job-level failure record (recommended):**
```
AdmissionRefusal(StrEnum): EXCEEDS_CAPACITY | UNKNOWN_REQUIREMENT | PROFILE_INCOMPLETE
JobFailure(frozen): error_class: ErrorClass; refusal: AdmissionRefusal | None; detail: str
Job.failure: JobFailure | None   # required iff state FAILED and the latest attempt is not FAILED/INTERRUPTED
```
`WAITING_RESOURCES → FAILED` requires `failure.error_class = RESOURCE` and a `refusal`. A new pure function, `permitted_take_recovery(job) -> frozenset[RecoveryKind]`:
- EXCEEDS_CAPACITY on a job **with a take** → `{RESOURCE_ADAPTATION}` (UD-5: always a new Take, which still needs approval).
- UNKNOWN_REQUIREMENT / PROFILE_INCOMPLETE → `{}`. Adapting cannot make an unknown requirement known. The route is calibration (F.2(f), I-6).
- A job **without a take** (for example a transcode) → `{}`. UD-5 defines adaptation as a new Take, so a take-less job has no adaptation path. A human re-plans it as a new job with `source_job_id` (I-12).

### C.6 Crash-loop breaker (UD-7)
```
BreakerEventKind(StrEnum): TRIPPED | RESET | QUARANTINE_LIFTED
BreakerEvent(frozen): event_id; kind; at (aware); by_name (RESET/LIFT: human, required)
                      binding_id (TRIPPED: quarantined registry binding); attempt_ids (TRIPPED: the K counted interrupts)
                      k: int; window_s: int                     # the K and T in force, recorded on the event
breaker_verdict(interrupts, events, *, k, window_s, now) -> BreakerVerdict(tripped, count_in_window, should_trip, quarantined)
```
- **Persistence:** append-only events (global DB, ADR-0004). The current state is derived from the last TRIPPED/RESET and the counted interrupts since `max(now - T, last RESET at)`. The domain is clock-free: `now` is passed in.
- **Trip:** `count ≥ K` while not tripped ⇒ `should_trip`. The scheduler (a later milestone) records TRIPPED. The queue is paused (no new dispatch), and the registry binding of the attempt that reached K is quarantined.
- **Reset:** human only (RESET). Lifting a quarantine is a separate human action (QUARANTINE_LIFTED). Nothing resets automatically.
- **K and T** live in configuration (`studio.toml [recovery.breaker]`, WT-B), never in the domain. They are provisional and unset at first (I-8). Fail-closed rule while unset (PROPOSED): any counted interrupt pauses the queue, which is equivalent to K=1. This is a safety rule, not a calibrated threshold.

### C.7 Startup interruption marking (idempotent)
`startup_interruptions(jobs, attempts, *, boot_id, host_boot_at) -> tuple[Transition, ...]`, pure:
- Selects only attempts in PENDING/RUNNING/INGESTING. Each goes to INTERRUPTED with cause `HOST_RESTART` if `started_at < host_boot_at`, else `STUDIO_PROCESS`, and with `interrupted_boot_id = boot_id`.
- Their jobs move RUNNING/INGESTING → INTERRUPTED. A job in WAITING_RESOURCES with a PENDING attempt moves to READY (an existing edge).
- **Exactly once:** INTERRUPTED attempts are terminal and never selected again. Persistence applies all transitions in one transaction keyed by `boot_id`, so a second run in the same boot finds nothing.

## D. Approvals and invalidation (UD-3, UD-5, UD-6, DM-2, DM-8, DM-9)

### D.1 Approval model changes (PROPOSED)
- `Approval += stale_at: datetime | None` (required iff STALE) and `stale_codes: tuple[ChangeKind, ...]`. `stale_reason` stays as human text.
- **DM-8:** `APPROVAL_TRANSITIONS[REJECTED] = ()`, so a rejection is final, matching Take REJECTED being terminal (`states.py:212` vs `:295`). Gate staleness stays a *gate* state (`GATE_TRANSITIONS` unchanged). Consequence: STALE now arises only from PENDING or APPROVED, so "STALE with `decided_at` set" unambiguously means "was approved".
- **As-of evaluation (DM-2):** `approval_valid_at(a, t)` = `a.decided_at ≤ t ∧ (a.state is APPROVED ∨ (a.state is STALE ∧ a.decided_at is not None ∧ a.stale_at > t))`. For an adapted take, `t` = `started_at` of attempt #1 of its job. If none has started yet, the approval must be APPROVED now. Later staleness therefore never retroactively invalidates a take that was produced legitimately (`validation.py:212` today checks the current state).
- **DM-9:** at most one *current* approval (PENDING, APPROVED or REJECTED) per `(subject, purpose)` (`approval.multiple_current`). An APPROVED take needs a current APPROVED CONTENT_REVIEW, and a REJECTED take needs a current REJECTED CONTENT_REVIEW (`state.take_rejection`).
